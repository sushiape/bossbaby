# Route Supabase-generated links by type

Auth emails triggered from the Supabase dashboard — a staff invite, a password
reset — carry no destination of their own. The dashboard exposes no field to set
one, so the link falls back to the project's Site URL. Site URL therefore points
at `/redirect`, a static page whose only job is to read the arriving link's type
and forward it to the page that handles it, carrying the link's fragment through
unchanged. It is a plain HTML file served ahead of the site's catch-all rewrite,
not a route in the React app: the forward must not wait on the app's bundle, and
nothing on the page may load a Supabase client.

Pointing Site URL directly at `/admin` was the obvious alternative and would
work today, with no code at all. It was rejected for two reasons. Site URL is
not only the no-destination fallback: it is also where links land when their
destination fails the Redirect URLs allow list, so aiming it at the workspace
would quietly deliver misrouted people to the staff door. And it is a single
global default for every auth email the project sends, which stops being correct
as soon as App Sign-Up begins confirming public users — they would arrive at the
staff workspace. Deciding per link type is what survives both.

`/redirect` forwards `invite` and `recovery` to `/admin`, and sends everything
else — unknown types, ordinary visits with no fragment — to `/` silently. It
reads the fragment as an opaque string and calls no Supabase auth method: the
fragment is the credential, and the staff client is deliberately the only client
with `detectSessionInUrl` enabled, so that consuming a staff link can never
clobber a Participant's anonymous session (see ADR-0002). Links generated by the
site's own code are unaffected — they pass `redirectTo` explicitly and never
touch this path.

The cost is that Site URL becomes load-bearing configuration: `/redirect` exists
because a dashboard field points at it, and nothing in the deployed site makes
that visible. The path is load-bearing too — it is spelled in the dashboard, in
the rewrite, and in the filename, and all three must agree. Changing Site URL silently breaks staff onboarding, and the
failure is delayed — an invited person's first visit still appears to work. This
ADR is the record of that dependency. The benefit is that dashboard-generated
links, which the team cannot control the destination of, arrive somewhere that
knows what to do with them.
